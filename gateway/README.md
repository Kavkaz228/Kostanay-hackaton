# Заводской HTTP-шлюз

`bridge.py` принимает измерения от согласованного адаптера контроллера, передаёт их в Allur Twin и выполняет подтверждённые команды через этот адаптер. Реального оборудования или показаний внутри шлюза нет. Без настроенного адаптера запуск завершает циклы ошибкой и не сообщает об успешном подключении.

## Интерфейс адаптера контроллера

Оба запроса используют `Authorization: Bearer <controller_key>`. TLS-сертификат проверяется средствами Python. Если нужна внутренняя CA, добавьте её доверенный сертификат в образ или примонтируйте bundle и задайте `SSL_CERT_FILE` через локальный Compose override. Не отключайте проверку TLS.

`GET /telemetry`:

```json
{
  "remote_control_enabled": true,
  "measurement": {
    "timestamp": "2026-10-06T10:00:00Z",
    "robot_id": "ROBOT-ID-FROM-CONTROLLER",
    "operation": "welding",
    "cycle_status": "In_Progress",
    "controller_mode": "automatic",
    "safety_state": "normal",
    "joint_temperature_c": 42.5,
    "electrode_count": 120
  }
}
```

Это пример структуры, не замена чтения контроллера. Передавайте фактическое время исходного измерения и фактическое аппаратное разрешение. Нельзя обновлять timestamp старых данных, чтобы они выглядели свежими. Синхронизация часов сервера, шлюза и контроллера обязательна. `measurement` соответствует JSON API Allur Twin, до последнего доступного датчика. Не добавляйте туда `remote_control_enabled`: он находится на внешнем уровне ответа адаптера.

`POST /commands`, дополнительно `Idempotency-Key` равен `command_id`:

```json
{
  "command_id": "UUID-сервера",
  "robot_id": "ROBOT-ID-FROM-CONTROLLER",
  "action": "hold",
  "speed_percent": null,
  "expires_at": 1791284430.0
}
```

Адаптер обязан сам проверять идентификатор робота, срок Unix UTC, аппаратные разрешения и диапазоны. Разрешены только `hold`, `resume`, `set_speed_percent`. Соответствие этих действий конкретным функциям изготовителя задаётся при пусконаладке. Адаптер должен сохранять обработанный `command_id`, не выполнять его повторно и возвращать прежний результат при повторном запросе.

Ответ после достоверного подтверждения оборудования:

```json
{
  "command_id": "UUID-сервера",
  "result": "succeeded",
  "hardware_acknowledged": true,
  "detail": "Описание результата от контроллера"
}
```

`result` — `succeeded` либо `failed`. HTTP 200 сам по себе не доказывает выполнение; нужны совпадающий ID, подтверждение оборудования и конечный результат. Таймаут, неоднозначный ответ или HTTP-ошибка после начала отправки превращаются в `uncertain`, без повторной физической записи. Время ответа ограничено 8 секундами; длительные команды требуют подходящего адаптера и отдельного согласованного контракта, а не преждевременного `succeeded`.

## Настройка

1. Сначала создайте робота в Allur Twin загрузкой реального первого измерения через CSV или существующий ключ приёма телеметрии. В учётной записи администратора выберите этого робота и создайте отдельный ключ заводского шлюза. Он действует до 30 дней по умолчанию, допускается отзыв; ключ привязан к одному роботу.
2. Скопируйте `gateway.example.json` в `gateway.json`. Укажите URL Allur Twin без `/api`, базовый URL адаптера и тот же `robot_id`. Задайте разрешённый предел скорости по регламенту площадки. `allow_resume` по умолчанию false. `allow_plain_http` допускается только для отдельно защищённой доверенной сети, не для открытого сетевого соединения.
3. Создайте локально `.secrets/gateway_key` и `.secrets/controller_key`. Каждый файл содержит только соответствующий секрет. Ограничьте доступ администраторами установки. Реальная конфигурация, журнал и секреты исключены из дистрибутива.
4. В папке `gateway` выполните `docker compose up --build -d --wait`. Один экземпляр обслуживает одного робота; для следующего используйте отдельный Compose-проект и отдельную конфигурацию/том/ключ.
5. Проверьте обновление реальных показаний, статус защиты и журнал. На сервере Allur Twin физическое управление включается через `PHYSICAL_CONTROL_ENABLED=true` и пересоздание API только после пусконаладки. Сначала проверьте действия в согласованном режиме испытаний с ответственным специалистом.

Система не является safety PLC. Защитное ограждение, разрешение дистанционного управления, аварийный останов и допустимые скорости должны контролироваться самим оборудованием. Наличие web-подтверждения не заменяет местный технологический регламент.

## Сбои и восстановление

Постоянный том `gateway_state` содержит SQLite-журнал. Он фиксирует намерение перед физической записью и сохраняет результат до подтверждения API. При перезапуске запись с незавершённым выполнением становится `uncertain`; шлюз не повторяет её. Повторяется только доставка телеметрии с Idempotency-Key или доставка результата серверу.

После неизвестного результата проверьте журнал и фактическое состояние контроллера. Затем администратор Allur Twin выбирает команду в «Учётная запись» → «Сверка результата с контроллером», указывает результат и документированное основание. Сверка не выдаёт новую команду. При отозванном ключе или несовместимом ответе API журнал может остаться в ожидании доставки: это преднамеренная остановка обмена, требующая разбора администратором.

Не удаляйте `gateway_state`, чтобы «снять» ошибку. Не откатывайте базу сервера и журнал шлюза независимо друг от друга при включённом оборудовании. После восстановления старой копии отключите физическое управление, остановите шлюз, сверьте все выданные/подтверждённые команды с контроллером и только затем продолжайте работу. Адаптер контроллера должен сохранять собственную дедупликацию команд независимо от перезапуска шлюза.

Контейнер не публикует порты, работает без root и с файловой системой только для чтения, кроме своего журнала. Проверка работоспособности требует успешного цикла за последние 30 секунд. `docker compose logs --tail 100 gateway` показывает класс ошибки без ключей и содержимого производственных сообщений. Ротация журнала контейнера включена.
