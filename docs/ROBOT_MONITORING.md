# Мониторинг роботов и рекомендации

Раздел «Мониторинг роботов» показывает проблемы в поступивших измерениях, рекомендации и подтверждение реакции сотрудника. Сервер проверяет показания каждые 10 секунд независимо от открытого браузера и состояния производственной симуляции. Интерфейс получает обновления каждые 10 секунд; закрытый браузер не показывает всплывающие уведомления, но события остаются в базе.

## Подключение данных

1. Передавайте показания роботов через существующий `POST /api/robots/measurements` с ключом интеграции либо загружайте CSV в разделе данных. CSV содержит историю: он не заменяет непрерывную передачу показаний.
2. В настройках робота задайте ожидаемый интервал передачи и предупреждающие/критические границы датчиков по документации оборудования. Универсальные температуры или значения вибрации не подставляются.
3. Заполните справочник кодов ошибок: описание, важность и утверждённое действие. Эти рекомендации доступны сразу, даже без ИИ.
4. Откройте «Мониторинг роботов». При отсутствии измерений система сообщает об ожидании данных. Учебный SCADA-стенд и его уведомления остаются отдельным источником.

## Цикл реакции

- При обнаружении отклонения создаётся событие с роботом, участком, временем измерения и основанием. Повторные проверки той же проблемы не создают дубликаты.
- Усиление проблемы снова требует внимания сотрудника. Новые проблемы видны через счётчик и уведомление в приложении.
- Сотрудник принимает событие в работу. Эта отметка общая для сотрудников установки и не означает устранение неисправности.
- Свежие нормальные показания по соответствующему датчику закрывают отклонение. Пропавшая связь или отсутствие поля датчика не означают, что проблема устранена.
- После подтверждённого восстановления повторное отклонение создаёт новое событие. История хранится в PostgreSQL.

## Роль локального ИИ

Для запуска модели выполните `./start-ai.ps1`. Используется Ollama и модель из `AI_MODEL`, по умолчанию `qwen3:4b`. Интернет требуется для первоначальной загрузки образа и весов; производственные данные служба модели обрабатывает во внутренней сети Docker.

ИИ получает контекст обнаруженного события и предлагает диагностические действия. Он не подтверждает причину поломки и не отправляет команды роботу. Рекомендация по заданному правилу и текст ИИ показаны отдельно. Пока модель занята или недоступна, обнаружение проблем и уведомления продолжают работать; интерфейс показывает состояние ИИ без подстановки вымышленного ответа.

`MONITORING_AI_ENABLED=false` в `.env` отключает фоновые обращения к модели после пересоздания API. Проверка показаний продолжает работать. Контур мониторинга не включает физическое управление и не выполняет ремонт, закупку или отправку сообщения за пределы приложения.

## API

- `GET /api/monitoring` — состояние проверки и список событий; доступно авторизованным сотрудникам.
- `POST /api/monitoring/{id}/acknowledge` — принять событие в работу; оператор или администратор, с CSRF-токеном сессии.

Результаты проверки относятся к поступившим данным и заданным порогам. Для достоверного мониторинга реального цеха нужны актуальный поток телеметрии, корректное время измерений и нормы конкретного оборудования.

## Проверка реализации

- Полный набор серверных тестов: 185 успешно. После уточнения контекста ИИ повторно прошли все 12 тестов мониторинга.
- Браузерный сценарий проверяет фоновое обнаружение, уведомление на другом экране, принятие в работу, усиление проблемы, восстановление по свежим данным и сохранение истории. Проверена ширина экрана 390 px.
- Настоящая локальная модель `qwen3:4b` проверена через `ops/monitoring_ai_check.py` в отдельной временной базе: сформировала рекомендации, команд роботу не создано. Последний проверочный ответ занял около 23 секунд; время зависит от оборудования и нагрузки.
