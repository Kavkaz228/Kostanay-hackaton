# Эксплуатация Allur Twin 2.0

## Модель поставки

Одна организация — отдельная папка установки, Docker Compose project, база PostgreSQL, секреты, резервные копии и доменное имя. Не копируйте `.env`, `.secrets`, `backups`, Docker volumes и данные заказчика в дистрибутив другого клиента. Поставляется исходный код и инструкции; коммерческие права на название Allur и конкретные данные определяет владелец продукта.

Поддерживается один сервер и один процесс API на базу. PostgreSQL advisory lock блокирует запуск второго владельца состояния. При потере соединения владельца процесс завершается; Docker перезапускает его, и состояние перечитывается из базы. Увеличивать `--workers` или число реплик API нельзя. Автоматического переключения на второй сервер в этой версии нет.

## Первое размещение

Нужны Linux containers и Docker Compose 2.24.4+ (`!override` в тестовой конфигурации). На Windows: `./start.ps1`. Скрипт генерирует уникальные секреты в контейнере, собирает приложение и запускает сервисы web и backup. На Linux эквивалент:

```sh
docker run --rm -v "$PWD:/workspace" -w /workspace python:3.12-slim@sha256:02108f5d322dd89f1c9e552442c25acb0543dfdbc455693a5599624f20d9155d python ops/init.py
docker compose up --build -d --wait web backup
```

Откройте http://localhost:8088. Начальный логин `admin`, временный пароль находится в `.secrets/bootstrap_password`. После первого входа приложение требует новый пароль. Создайте именные учётные записи и второго администратора для восстановления доступа. Пароли от 15 до 128 символов; предпочтительны уникальные длинные фразы. Не публикуйте секреты в сообщениях, Git или скриншотах.

Каталог `.secrets` должен быть доступен только администраторам сервера. На Linux инициализатор задаёт каталогу права 0700; отдельные файлы монтируются через Compose secrets и читаются непривилегированным API. На Windows дополнительно ограничьте доступ к папке средствами NTFS. Секреты не входят в образы. Docker administrators и владельцы резервных копий имеют привилегированный доступ к установке.

Для каждого клиента используйте `COMPOSE_PROJECT_NAME=customer_name` в его `.env` либо `docker compose -p customer_name ...`. Для отдельных установок на одном сервере задайте разные PORT, каталоги и домены. Встроенный HTTPS-шлюз занимает 80/443: для нескольких клиентов на одном сервере используйте общий администрируемый TLS-прокси с разными доменами. Не размещайте разных клиентов по разным путям одного origin.

## HTTPS

По умолчанию публикуется только loopback-порт; HTTP предназначен для локальной проверки. Для сетевого размещения задайте реальный DOMAIN в `.env`, направьте DNS на сервер, откройте 80/443, затем:

```sh
docker compose -f compose.yaml -f compose.production.yaml up --build -d --wait web backup gateway
```

Caddy получает и продлевает сертификат; API включает Secure cookie и проверку origin `https://DOMAIN`. При корпоративном прокси вместо Caddy задайте `COOKIE_SECURE=true`, `PUBLIC_ORIGIN=https://ваш-домен`, передавайте исходный Host и завершайте TLS на доверенном прокси. До передачи клиенту проверьте сертификат и вход именно по его домену. Конкретный публичный домен и выдача сертификата не могут быть проверены на локальной установке без DNS клиента. Для доступа из интернета рекомендуется корпоративный VPN или шлюз с MFA; встроенного SSO/MFA в приложении нет.

## Доступ и интеграции

После объединения со SCADA ключ датчиков также разрешает `POST /api/scada/readings`: тело `{"readings": [...]}`, до 1000 записей, повтор защищён уникальным `record_id` каждой записи. Доступ к складу, закупкам, ТО и чтению данных по этому ключу запрещён. Формат и привязка датчиков: [SCADA_MERGE.md](SCADA_MERGE.md). Следующее описание Idempotency-Key относится к API роботов.

* Наблюдатель читает данные и выгружает CSV.
* Оператор дополнительно импортирует данные, управляет моделью, подтверждает события, меняет правила и выполняет сценарии.
* Администратор дополнительно управляет пользователями, ключами и читает аудит.

Сервер проверяет права на каждом запросе. Cookie HttpOnly/SameSite=Strict, сессия до 8 часов, изменения требуют CSRF-токен. Пароли хранятся как scrypt N=131072, r=8, p=1 с индивидуальной солью. Ключи и идентификаторы сессий хранятся в виде SHA-256 случайного высокоэнтропийного значения. Кэш проверки сессий живёт до 30 секунд; управление доступом через приложение немедленно очищает кэш. Смена пароля отзывает все сессии. Самому себе отключить доступ или сменить роль через административный экран нельзя.

Для восстановления утраченного пароля администратор сервера выполняет интерактивно:

```sh
docker compose exec api python -m app.admin reset-password admin
docker compose restart api
```

Пароль вводится скрыто, в командную строку и историю shell не помещается. Перезапуск обеспечивает немедленный отзыв кэшированных сессий после аварийного изменения через CLI.

Ключ интеграции создаётся в «Учётная запись → Ключи интеграций», показывается один раз, имеет срок действия и может быть отозван. Для роботов разрешён POST `/api/robots/measurements`; читать данные и управлять моделью по ключу нельзя. Заголовки: `Authorization: Bearer <ключ>`, `Idempotency-Key: <ID пакета от 8 до 128 ASCII символов>`. Тело JSON: `{"measurements": [...]}`. До 1000 строк за запрос. Сохраняйте ID и содержимое пакета до получения ответа: после разрыва/503 повторяйте тот же пакет с тем же ID. Повтор возвращает сохранённую квитанцию; другое содержимое с прежним ID возвращает 409. Для каждого робота время новых измерений строго возрастает. Пропуск датчика не превращается в ноль. Этот ключ не разрешает управление оборудованием. Для подтверждённых физических команд предусмотрен отдельный ключ заводского шлюза и выключенный по умолчанию режим управления; см. MANUFACTURING_AND_AI.md и gateway/README.md.

## Резервные копии и восстановление

Сервис backup выполняет согласованный `pg_dump -Fc` при запуске и каждые 6 часов, проверяет читаемость архива, пишет SHA-256 и оставляет копии за 14 дней. Ошибка прекращает процесс и вызывает перезапуск; отсутствие успешной копии более 7 часов делает сервис unhealthy. Ручная копия: `./backup.ps1`. Это полный снимок базы, включая пользователей и настройки. SQL-транзакции обеспечивают согласованность дампа при работающем приложении.

Проверка копии: `./restore-check.ps1 -Backup ./backups/allur-....dump`. Скрипт создаёт временный PostgreSQL без сети, действительно восстанавливает архив и читает восстановленные таблицы; рабочую базу не меняет. Не считайте наличие файла доказательством восстанавливаемости без этой проверки.

Хранение на том же диске не защищает от потери сервера. Настройте зашифрованное копирование `backups` во внешнее хранилище вашей организации и мониторинг его выполнения. Ключ шифрования храните отдельно. Эти настройки зависят от инфраструктуры клиента и не имитируются в приложении. При периоде 6 часов потенциально теряется до 6 часов новых данных; фактическое время восстановления зависит от размера базы. Для более строгого RPO/RTO необходимы WAL-архивирование и резервный сервер.

Восстановление рабочей установки выполняется в согласованное окно обслуживания:

1. Сделайте дополнительную копию текущей базы. Остановите web, api и backup, оставив db.
2. Проверьте выбранный архив через restore-check и запишите его SHA-256.
3. Скопируйте архив в db: `docker compose cp <файл> db:/tmp/restore.dump`.
4. **Следующая команда заменяет содержимое рабочей базы**: `docker compose exec -T db pg_restore -U allur -d allur --clean --if-exists --no-owner --no-acl --single-transaction --exit-on-error /tmp/restore.dump`.
5. Запустите `docker compose up -d --wait web backup`, проверьте вход, количество измерений, правила и последний импорт. После восстановления старой копии отзовите действующие на тот момент ключи/сессии, если их безопасность вызывает сомнения.

## Обновления и наблюдение

Перед обновлением сделайте и проверьте дамп, зафиксируйте версии/идентификаторы образов. Установите релиз в тестовой среде, запустите `./test.ps1`. Затем в окно обслуживания обновите рабочие образы и запустите Compose. Формат хранения v2 автоматически переносит роботные строки из старого JSON-снимка в индексированную таблицу внутри одной транзакции. Повторный запуск не дублирует строки. Версия ниже сохранённой отвергается; откат выполняется восстановлением соответствующего дампа и образа, а не запуском старого кода поверх новой схемы.

Проверяйте `docker compose ps`, `/api/health`, статус backup и свободное место на диске. Здоровье включает базу и состояние фонового обработчика. Диагностика в «Учётная запись» показывает число сессий, измерений и размер базы. Каждый ответ содержит X-Request-ID; сервер пишет метод, путь, статус и длительность без тела, cookies и ключей. Изменения приложения и аудит фиксируются одной транзакцией. Логи контейнеров ограничены 5 файлами по 10 МБ на сервис. Настройте внешнее оповещение ответственных при unhealthy, нехватке диска и отсутствии свежей внешней копии.

Роботная история не ограничена 200 000 строками и не переписывается целиком при каждом пакете. В памяти остаются начальная, последняя и последние непустые записи датчиков; полная история хранится в PostgreSQL. Для аналитики один выбранный период ограничен 100 000 строками; при превышении требуется сузить период. Экспорт всей роботной истории передаётся порциями. CSV ограничен 5 МБ и 20 000 строк на файл, до 1000 роботов. Производственный CSV пяти участков сохраняет ограничение 200 000 строк серии. Карточки с графиками и аналитикой используют готовый расчёт до 5 секунд; экран показывает время расчёта и опрашивает сервер каждые 2 секунды. Изменение настроек немедленно сбрасывает этот кэш. Прямое чтение истории и CSV-экспорт используют сохранённые записи без этой задержки. Приложение ничего не удаляет из истории автоматически; срок хранения и архивирование нужно назначить по регламенту клиента, контролируя диск.

Проверенный профиль нагрузки и измеренные задержки приведены в VERIFICATION.md. Нагрузочная проверка: `./test.ps1 -Load`; она создаёт отдельные секреты и базу <имя установки>-check. 450 сессий не означают 450 одновременных тяжёлых what-if расчётов: тяжёлые операции ограничены, при перегрузке возвращается 429 с предложением повтора. Нельзя обещать SLA, допустимое число роботов и период хранения без испытания фактического потока и дисков заказчика.

Использованные технические рекомендации: [OWASP — хранение паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP — управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html).


## Дополнения версии 2.1

Контроль качества, отчёты кейса, команды и ключи шлюзов добавляются отдельными таблицами автоматически; существующие измерения и состояние симуляции сохраняются. Перед обновлением обязательна копия базы. Для запуска ИИ используется ./start-ai.ps1; том ollama_models сохраняет веса отдельно от PostgreSQL. Закрытая сеть inference не должна подключаться к внешнему маршруту в рабочем размещении.

После восстановления старой копии при наличии физического оборудования сначала оставьте PHYSICAL_CONTROL_ENABLED=false и остановите заводские шлюзы. Сверьте очередь с журналами контроллеров, включая уже выданные команды; нельзя возобновлять её автоматически из старого дампа. Постоянный журнал шлюза и дедупликация контроллера описаны в gateway/README.md.

Новые показания и отчёты: docs/MANUFACTURING_AND_AI.md. ИИ обрабатывает один запрос одновременно; 450 пользовательских сессий не являются 450 одновременными запросами генерации.
